## 1. What this project is

Diffusion-based virtual try-on works entirely in 2D: it has no model of body or garment
geometry, so a garment can be placed incorrectly and is inconsistent across viewpoints.
MeshVTON conditions a **frozen** pretrained diffusion model (FLUX.1-Fill-dev) on
**screen-space renderings of a posed 3D body and garment** — surface normals, depth and
silhouette — injected through a **zero-initialised control branch of 0.8 M trainable
parameters**. The backbone is never fine-tuned as a whole; only the control branch and a
LoRA adapter are trained.

The pipeline for one image is:

```
person photo ──► HMR2 (4D-Humans) ──► SMPL-X body ──┐
                                                    ├─► LBS drape ─► pyrender (screen space)
garment mesh (CLOTH3D) ─────────────────────────────┘         │
                                                              ▼
person photo ─► human parsing ─► agnostic image + inpaint mask ─► FLUX.1-Fill + control branch ─► output
```

**Headline result** — the report's Table III (golden set, 100 pairs, frontal):

| Method | geo_IoU ↑ | Specificity ↑ | Placement | ΔE ↓ |
|---|---|---|---|---|
| Fill (spatial), untrained | 0.330 | **+0.005** ≈ zero — no dependence on the mesh | 0.769 | **14.85** |
| MeshVTON, geometry branch **OFF** | 0.511 | +0.088 | 0.627 | 27.83 |
| MeshVTON, geometry branch **ON** | **0.688** | **+0.229** | 0.508 | 24.98 |

Roughly **three fifths** of the specificity is attributable to the geometry branch; the
remainder comes from the appearance reference, which is itself rendered from the same mesh.
The effect holds for all twenty evaluated persons. Placement is read alongside specificity
rather than maximised: as the model follows the mesh it necessarily departs from the garment
the person was already wearing. §6 lists which command reproduces which table and figure.
A methodological contribution of the work is the *mesh specificity* metric itself: agreement
with the supplied silhouette (`geo_iou`) is self-referential — it rewards a model for
following the conditioning even when the conditioning is misplaced.

## 3. Environment

Python ≥ 3.10 (developed on 3.13 locally and on Colab's 3.11). This environment is
completely independent of the earlier v1 prototype and must not be mixed with it.

```bash
pip install -r v2/requirements.txt
```

`v2/requirements.txt` covers everything needed for §4A (the tests). The full pipeline needs three
further components that are installed separately because they are large, compile, or require a
licence acceptance — the exact commands are in §4C.

Hardware: training and inference need an A100/L4-class GPU with ≥ 40 GB VRAM
(FLUX.1-Fill in bfloat16 does not fit on a T4). Everything in §4A and §4B runs on a CPU laptop.

## 4. How to run — three levels, in increasing cost

Because the model depends on ~24 GB of licence-gated weights and on datasets that cannot be
redistributed, **no self-contained executable is provided**. The three levels below are
ordered so that an examiner can verify progressively more of the system with progressively
more effort; level A alone takes about a minute and needs no GPU, no data and no weights.

### A. Verify the code without GPU, data or model weights — ~1 minute

```bash
pip install -r v2/requirements.txt
python -m pytest v2/tests -q
```

Expected: **71 passed**. These are not smoke tests; they cover the parts of the contribution
that can be checked without the backbone:

- `test_parity.py` — enforces that training, synthetic generation and inference all build
  their conditioning through the *same* function (the project's central invariant, §7)
- `test_camera.py` — the weak-perspective → full-frame perspective camera derivation
- `test_lbs_drape.py` — the K-NN garment-to-body binding and local frame transfer
- `test_training_core.py`, `test_data_and_loop.py` — rectified-flow loss, the training loop
  learns on a synthetic task and resumes correctly from a checkpoint
- `test_eval.py` — the metrics, including the rule that an uncomputable metric returns
  `None`/"n/a" and never `0.0`
- `test_data_contract.py`, `test_phase1.py` — the on-disk sample format

### B. Inspect the geometry pipeline without diffusion — minutes, CPU

These scripts read and write images only; they never load the diffusion backbone. They
require the 3D garment meshes and the person photos (§2), but no GPU and no FLUX weights.

```bash
python v2/scripts/calibrate_hang.py  --idm-repo <IDM-VTON path>   # garment hang-height sweep
python v2/scripts/calibrate_scale.py --idm-repo <IDM-VTON path>   # garment scale sweep
python v2/scripts/validate_camera.py --idm-repo <IDM-VTON path>   # camera gate: reprojection IoU >= 0.70
python v2/scripts/mesh_specificity.py --sets ckpt_control_on_july ckpt_control_off_july
python v2/scripts/placement_iou.py   --idm-repo <IDM-VTON path>
python v2/scripts/make_figures.py    --sets ckpt_control_on_july
```

The calibration scripts reproduce, with no gradient step at all, the paper's claim that two
uncalibrated scalars cost more than half of the achievable mesh specificity.

### C. Full pipeline — Google Colab, A100/L4, several hours

The notebooks in `v2/notebooks/` are the ones actually used for the reported results, and they
are the shortest path to a working environment. `MeshVTON_demo.ipynb` is the recommended
entry point: its first three cells build the whole environment, and the remaining cells run
try-on and the control-branch ablation on uploaded photographs.

The extra installs (also performed by that first cell) are:

```bash
pip install "git+https://github.com/shubham-goel/4D-Humans.git"     # HMR2 body estimation
git clone https://github.com/yisol/IDM-VTON                          # human parsing + OpenPose
pip install smplx pyrender onnxruntime                               # SMPL-X + headless renderer (EGL)
```

Then, with the datasets and the checkpoint in place:

```bash
# end-to-end, resumable, one command (stages: check → camera → smoke → synth → baseline → train → eval)
python v2/scripts/colab_pipeline.py --idm-repo /content/IDM-VTON

# or stage by stage:
python v2/scripts/generate_synthetic.py --garments <garments_3d> --num 2000   # synthetic multi-view data
python v2/scripts/preprocess_vitonhd.py --images <vitonhd/train/image> --cloth <vitonhd/train/cloth> \
                                     --idm-repo /content/IDM-VTON          # real paired data
python v2/scripts/build_golden_set.py  --vitonhd-test <test/image> --garments <garments_3d>
python v2/scripts/zero_shot_baseline.py --variant fill_spatial --idm-repo /content/IDM-VTON
python v2/scripts/train_stage1.py --config v2/configs/stage1_singleview.yaml --max-steps 4000
python v2/scripts/eval_checkpoint.py --checkpoint <ckpt_004000.pt> --idm-repo /content/IDM-VTON \
                                  --limit 50 --use-texture --hang-pad -0.12 --garment-scale 1.25
```

The last command is the one that produced the table in §1: it runs the golden set twice, once
with the geometry branch on and once with it off, which is the paper's central ablation.
Note the two calibrated constants (`-0.12`, `1.25`) — they are the defaults inside
`v2/meshvton2/conditioning/builder.py` for the photo path and are passed explicitly here for
clarity.

**Which regime to use:** the reported results come from the *textured* regime (the July
checkpoint, 4000 steps, 70 % real VITON-HD + 30 % synthetic, `--use-texture`). A second
textureless regime exists and is weaker on every metric. `v2/docs/REGIMES.md` gives both
configurations and explains how to switch.

## 7. Design rules the code enforces

These are stated because they explain otherwise surprising choices in the code, and several
are enforced by tests:

1. **One conditioning function.** Only `builder.py::build_conditioning` produces conditioning,
   for every caller. A train/inference mismatch was the single most costly bug in the earlier
   prototype; `v2/tests/test_parity.py` now makes it impossible to reintroduce silently.
2. **One resolution**, 768 × 1024, everywhere.
3. **No RGB in the control branch.** Geometry channels only (normal, depth, silhouette);
   appearance enters solely through the reference image.
4. **No metric lies.** A metric that cannot be computed returns `None` / "n/a", never `0.0`.
5. **No logic in the notebooks.** They call scripts; the logic is in the library.

## 8. Known limitations

- **Appearance fidelity is the main limitation.** The geometry branch carries shape but no
  appearance, so colour and pattern must travel through the reference frame, and that channel
  is the bottleneck. The report rules out an inference-time cure — guidance scale, the mask
  regime, the control-injection strength and the compositing step were each swept and each was
  negative (`v2/scripts/sweep_guidance.py`, `v2/scripts/sweep_inference.py`) — and rules out an
  undertrained checkpoint, since the loss plateaus after roughly 125 of the 4,000 steps. The
  cause is localised to the training data: in the real-data branch (70 % of samples) no product
  photographs were available, so the appearance reference was cut from the garment the person
  was already wearing, which shares illumination, pose and drape with the target and reduces the
  task to something close to a copy. That shortcut does not transfer at inference, where the
  reference is a flat-lit render of a mesh. Restoring proper person↔product pairing is the first
  correction to make.
- **Skin-tone bias** was diagnosed and measured; the attempted correction was reverted and is
  discussed as a limitation in the report rather than being present in this code.
- **Stage 2 (multi-view consistency training) was not run.** The data path and the 4-view
  dataset exist in the code; the training budget did not.
